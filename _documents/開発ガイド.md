# 開発ガイド

## 新しいツールを作る

1. GitHub の「Use this template」で新しいリポジトリを作る（既定ブランチは `develop`）
2. clone してサブモジュールも取得する

    ```bash
    git clone --recurse-submodules https://github.com/vehiclevisionjp/<新しい名前>.git
    ```

3. 名前を置換する。中身、ファイル名、フォルダ名、ロックファイルが対象

    ```powershell
    ./scripts/New-FromTemplate.ps1 -Name VehicleVision.PleasanterTools.<ツール名>
    ```

4. `README.md`、`NOTICE`、`_documents/アーキテクチャ方針.md` を実態に合わせる
5. [開発運用](開発運用.md) の「GitHub の初期設定」を行う
6. `develop` へ最初のコミットを置く（初期リポジトリ作成のみ、直接配置してよい）

## 前提

- .NET SDK 10.0.100 以降（`global.json`。全リポジトリで同じ値。`latestFeature` で新しいパッチへ進む）
- Node.js 24 以降（Markdown の検査用）
- PowerShell 7 と bash（スクリプト用）

## 共通部品（Core）を使う

メール送信や DB の基盤は、各ツールへコピーせず、**共通部品（Core）を nuget.org から参照する**。
コピーは、直した側と直していない側を必ず生むため。何を Core に置き、何を置かないかは
[Core の「コア化の方針」](https://github.com/vehiclevisionjp/VehicleVision.PleasanterTools.Core/blob/master/_documents/%E3%82%B3%E3%82%A2%E5%8C%96%E3%81%AE%E6%96%B9%E9%87%9D.md)を読むこと。

| パッケージ | 中身 |
| --- | --- |
| `VehicleVision.PleasanterTools.Core.Mail` | メール送信（SMTP / Amazon SES / Azure Communication Services）、メッセージの組み立て、`MailOptions` |
| `VehicleVision.PleasanterTools.Core.Data` | 接続の解決と暗号化の検査、`DbTime`、起動時マイグレーションと排他、`SqlDialect` の汎用部分 |

```xml
<PackageReference Include="VehicleVision.PleasanterTools.Core.Mail" Version="0.1.0-preview.4" />
<PackageReference Include="VehicleVision.PleasanterTools.Core.Data" Version="0.1.0-preview.4" />
```

- **`nuget.config` もトークンも要らない**（nuget.org から取得する）。最新の版は nuget.org で確かめる
- **Core が持つ依存（Dapper・FluentMigrator・DB ドライバなど）を、ツール側で宣言し直さない。** 版のずれの原因になる。
  セキュリティの修正版へ固定する必要があるものだけを例外にして、理由をコメントに書く
- **アプリ固有の値は、引数で Core へ渡す。** 次の「DB を使うとき」の表のとおり、ツールごとに 1 か所（`<ツール名>Database` のような静的クラスが持つ `AppDatabase`）へまとめる
- Core の更新は、Dependabot が PR で配る。CI が通れば取り込む

## DB を使うとき

DB を使うツールは、**ツールごとに別の DB を持つ**（ツール同士で DB は共有しない）。

### 名前は、ツール ID から Core.Data の `AppDatabase` が導く

**手書きしない。** ツール ID（例: `questionnaire`）と、マイグレーションを置くアセンブリを渡せば、次の名前が決まる
（`<id>` は ID、`<ID>` はその大文字でハイフンは下線）。

| 値 | 規約 |
| --- | --- |
| SQLite の既定ファイル名 | `<id>.db` |
| RDBMS を選ぶ設定名 | `<ID>_DB_PROVIDER` |
| 接続文字列の設定名 | `<ID>_DB_CONNECTIONSTRING` |
| 暗号化を緩める設定名 | `<ID>_DB_ALLOW_INSECURE` |
| マイグレーションの排他のロック名 | `<id>-startup-migrations` |

```csharp
public static class <ツール名>Database
{
    public static AppDatabase Instance { get; } = new("<id>", typeof(<ツール名>Database).Assembly);

    // CA2255 は「ライブラリでの [ModuleInitializer]」への注意。ここは再利用するライブラリではなく、このツールのデータ層
#pragma warning disable CA2255
    [ModuleInitializer]
#pragma warning restore CA2255
    internal static void Initialize() => _ = Instance;
}
```

呼び出し側は `<ツール名>Database.Instance` から、`Migrator`・`ParseProvider`・`ResolveConnectionString`・`EnsureSecure` を使う。

- **ロック名は、ツールごとに別になる。** 同じ DB サーバを複数のツールが使うとき、名前が同じだと、別のツールのマイグレーションを待たせる。ID が一意であれば衝突しない
- メールの環境変数の接頭辞（`<ID>_MAIL_`）は、Core.Mail と Core.Data が互いを参照しないため、`AppDatabase` には含まれない。`MailOptions.FromConfiguration(configuration, prefix)` へ渡す

### マイグレーションの番号

- **ツールは 4 桁（1〜9999）**の番号を、ほかのツールと調整せずに使う（DB を共有しないので、衝突しない）
- **Core の共有マイグレーションは 5 桁（`M10001`〜）**で固定する。桁数で範囲が分かれ、同じ DB に同居しても衝突しない
- **公開したマイグレーションの変更も、番号の振り直しもしない。** 直すときは、新しいマイグレーションを足す
- マイグレーションは**ツールのアセンブリに置く**（`AppDatabase` の第 2 引数にそのアセンブリを渡す）

### 日時の持ち方

- **DB の列は、ネイティブの日時型（`AsDateTime2()`）にする。** 文字列で持たない
- **DB へ渡す時刻は `DbTime.ForDb` を通し、読んだ時刻は `DbTime.AsUtc` で UTC の印を付ける。** `DateTime.UtcNow` をそのまま渡さない
  （`ForDb` は秒未満を切り捨て、`DateTimeKind` を外す。MySQL の丸めと、PostgreSQL の時間帯の変換で、保存した時刻がずれるため）
- **`ToString("O")` など、`DbTime` を通さない書き方をしない。** 日時型の列へ入れると、時間帯の分だけずれる
- **時刻は秒単位で持つので、時刻を区切りにしたページ送りをしない。** 同じ秒の記録を取りこぼす。**件数の `offset`（`SqlDialect.Page`）で区切り、
  並びは `ORDER BY 時刻 DESC, Id DESC` のように、同じ秒でも定まる形にする**

### SQLite のモデル型

SQLite は、列挙型や名前つきコンストラクタを持つ型（record など）を、文字列・整数から戻せない。Core.Data は、**知らされたアセンブリの型だけ**を登録する。
`AppDatabase` を作るとき、マイグレーションのアセンブリは自動で知らされる。**モデル型が別のアセンブリにあるときだけ、第 3 引数以降で渡す。**
上の `[ModuleInitializer]` が、アセンブリの読み込み時に `Instance` を作るので、登録が必ず先に済む
（知らせないと、`A parameterless default constructor or one matching signature … is needed` で落ちる）。

実際の登録は SQLite の接続を作るときだけで、ほかの RDBMS の挙動は変わらない。

### SQL の方言差

- **汎用の方言差**（`Format` / `Quote` / `Page` など）は、Core.Data の `SqlDialect` を使う
- **ツール固有の SQL** は、`<ツール名>SqlDialect` のような別のクラスに置く（`static partial class` は別のアセンブリへまたげないため）。
  汎用側は `using static VehicleVision.PleasanterTools.Core.Data.SqlDialect;` で、そのまま呼べる

### テスト

DB の基盤は、Core が 4 RDBMS（SQL Server / PostgreSQL / MySQL / SQLite）で試す。
**ツールは、自分が使う RDBMS だけで、自分の SQL を試す。**

### 実機の DB のテスト（DatabaseConverter）

`tests/...Integration.Tests` は、環境変数 `DBCONV_TEST_SQLSERVER` / `DBCONV_TEST_POSTGRESQL` / `DBCONV_TEST_MYSQL` に接続文字列があるときだけ流れる（無ければスキップ）。
CI（`.github/workflows/integration.yml`）は `DBCONV_REQUIRE_ALL_RDBMS=1` を立てて、未設定なら落とす。
テストは Pleasanter の表を模した小さな表を**毎回落として作り直す**ので、検証用の空の DB にだけ向けること（本番や実データの DB に向けない）。

## ビルドとテスト

```bash
dotnet restore --locked-mode
dotnet build --no-restore -c Release
dotnet test --no-build -c Release
npm ci --ignore-scripts && npm run lint:md
bash scripts/sync-agents.sh --check
bash scripts/reference-isolation-check.sh
```

依存を追加・更新したら `--locked-mode` を外して `dotnet restore` し、`packages.lock.json` を更新してコミットする。

## 規約を変える

共通規約の編集元は `.github/copilot-instructions.md`。変更後に `bash scripts/sync-agents.sh` で `AGENTS.md` を再生成する。
